## Quality Over Speed · Engagement Over Variety · Consistent Progress Every 4 Weeks

---

## PHILOSOPHY SHIFT: 12 Weeks vs 36 Weeks

This is not a cram plan. It is a **skills transformation plan**.

The 12-week version treated mastery as a destination you sprint to.
This 36-week version treats mastery as a process of **deep internalization** — where you solve fewer problems but understand each one more thoroughly, where you design fewer systems but can explain every design decision under pressure, where you see the same concept from 4 different angles before calling it learned.

**The core tradeoff you're making:**
- ❌ Not: cover everything quickly
- ✅ Yes: deeply own 20 patterns/concepts that you can execute perfectly under interview pressure

**What engagement and consistency means concretely:**
- Same schedule every week (your brain learns the ritual, not just the content)
- Every topic is touched 3 times before you move on (read → solve → teach)
- You feel forward momentum every 4 weeks (measurable gate, not just "I studied")
- You don't context-switch too fast (patterns stay open for 2 weeks, not 2 days)

## PART 1: THE LEARNING LOOP (Every Topic Uses This)

The reason most engineers fail interviews despite "studying for months": they see a concept once, solve 10 problems, move on. The brain hasn't formed deep pathways.

**This plan uses a 3-touch model:**

```
Touch 1 — UNDERSTAND (Week A, Day 1)
  Read the concept. Draw it. Explain it to yourself in your own words.
  Don't solve problems yet. Just internalize the model.
  Time: 45–60 minutes

Touch 2 — APPLY (Week A, Days 2–5 + Week A Saturday)
  Solve 6–8 problems from Easy to Hard using this pattern.
  For each problem: 
    - Identify why the pattern applies before touching code
    - Write brute force first (even if you know the optimal)
    - State complexity before verifying
    - Note the specific variant of the pattern

Touch 3 — TEACH (Week B, Day 1)
  Before starting new content: write a 1-page explanation of
  last week's pattern as if teaching a junior engineer.
  Then solve 2 more problems from the pattern to test recall.
  Time: 45 minutes
  
Why it works: The act of teaching forces retrieval, not recognition.
Recognition fools you into thinking you've mastered something.
Retrieval is what happens in an interview.
```

### Weeks 7–8: Dynamic Programming — 1D → 2D → Knapsack

**Why DP gets 2 weeks immediately after trees?** DP is the most feared and most frequently tested pattern at SDE-3. Two weeks of consistent immersion (rather than one rushed week) is the difference between "I've seen DP" and "I can derive any DP solution."

**The 3-Step DP Method (internalize before touching any problem):**
```
Step 1 — Define the state: what does dp[i] represent?
Step 2 — Write the recurrence: dp[i] = f(dp[i-1], dp[i-2], ...)
Step 3 — Identify the base case: dp[0] = ?, dp[1] = ?

If you cannot do all 3 before coding, you don't understand the problem yet.
```

**Touch 1 (Week 7 Monday):** Draw the recursion tree for Fibonacci. Count how many times fib(3) is computed. Then draw the memoized version. This one exercise explains the entire value of DP.

**Week 7 Problem Set — 1D DP:**

| # | Problem | State Definition | Recurrence | Difficulty |
|---|---|---|---|---|
| 1 | Climbing Stairs (LC 70) | dp[i] = ways to reach step i | dp[i] = dp[i-1] + dp[i-2] | Easy |
| 2 | House Robber (LC 198) | dp[i] = max money up to house i | dp[i] = max(dp[i-1], dp[i-2] + nums[i]) | Medium |
| 3 | Coin Change (LC 322) | dp[i] = min coins to make amount i | dp[i] = min(dp[i - coin] + 1) for each coin | Medium |
| 4 | Longest Increasing Subsequence (LC 300) | dp[i] = LIS ending at index i | dp[i] = max(dp[j] + 1) for all j < i where nums[j] < nums[i] | Medium |
| 5 | Word Break (LC 139) | dp[i] = can we form s[0..i]? | dp[i] = any dp[j] where s[j..i] is in dict | Medium |

**Week 8 Problem Set — 2D DP + Knapsack:**

| # | Problem | State Definition | Recurrence | Difficulty |
|---|---|---|---|---|
| 6 | Unique Paths (LC 62) | dp[i][j] = paths to reach cell (i,j) | dp[i][j] = dp[i-1][j] + dp[i][j-1] | Medium |
| 7 | Edit Distance (LC 72) | dp[i][j] = edits to convert s1[0..i] to s2[0..j] | dp[i][j] = min(insert, delete, replace) | Hard |
| 8 | Longest Common Subsequence (LC 1143) | dp[i][j] = LCS of s1[0..i], s2[0..j] | dp[i][j] = dp[i-1][j-1]+1 if match, else max(dp[i-1][j], dp[i][j-1]) | Medium |
| 9 | 0/1 Knapsack (classic) | dp[i][w] = max value using first i items with weight limit w | dp[i][w] = max(dp[i-1][w], dp[i-1][w-wt[i]] + val[i]) | Medium |
| 10 | Partition Equal Subset Sum (LC 416) | dp[i][s] = can we make sum s with first i items? | dp[i][s] = dp[i-1][s] or dp[i-1][s-nums[i]] | Medium |

**Week 8 Teach-Back:** "1D DP vs 2D DP — how do you know which you need?" Write a decision rule. (Answer: if the state depends on 2 independent variables simultaneously, you need 2D. If state only depends on previous state(s) in one dimension, 1D suffices.)

### Weeks 9–10: Graphs — BFS, DFS, Topological Sort

**Why graphs after DP?** Graph traversal (BFS/DFS) uses the same recursive/iterative patterns from trees, and topological sort is essentially DP on a directed acyclic graph. By now, both mental models are warm.

**The Key Graph Insight to internalize before Week 9:**
> "A grid is a graph. Every cell is a node. Adjacent cells are edges. BFS on a grid = shortest path in unweighted graph. DFS on a grid = exhaustive exploration."

This single insight handles 40% of graph problems at interview level.

**Week 14 — Backtracking:**

The template before solving any backtracking problem:
```
function backtrack(state, choices):
    if is_solution(state):
        add state to results
        return
    for each choice in choices:
        make_choice(choice)
        backtrack(new_state, remaining_choices)
        undo_choice(choice)       ← THIS is what makes it backtracking
```

| # | Problem | State | Choices | Undo |
|---|---|---|---|---|

| 2 | Permutations (LC 46) | Current permutation | Any unused element | Remove added element |
| 3 | Combination Sum (LC 39) | Current combo + remaining target | Next element (allow repeat) | Pop last element |
| 4 | Palindrome Partitioning (LC 131) | Current partition | All valid palindrome prefixes | Pop last partition |
| 5 | N-Queens (LC 51) | Board state | Valid columns per row | Remove queen |

## PART 5: WEEKS 25–32 — HLD MASTERY

### The HLD Philosophy for SDE-3

At SDE-2 level, HLD is about knowing which components to name (cache, queue, database).
At SDE-3 level, it's about **owning the trade-off discussion**:

> "I chose eventual consistency here because the read/write ratio is 100:1 and users can tolerate 5-second stale data in their feed. If this were a payment system, I'd require strong consistency and accept the write latency."

That sentence signals SDE-3. Naming Redis doesn't.

**The 4 Core Concepts you must internalize before any case study:**
1. Caching (where, what, how, invalidation)
2. Consistency models (strong, eventual, CAP theorem implications)
3. Database selection (SQL vs NoSQL decision framework)
4. Async processing (message queues, delivery guarantees)

### Week 26: HLD Concept 2 — Consistency Models + CAP Theorem

**This is the concept most engineers get wrong.** Not because it's hard — because it's abstract. This week makes it concrete.

**Monday (1.5 hrs):**
- Strong consistency: every read sees the most recent write. Bank transactions. Booking systems. Requires all replicas to agree before confirming.
- Eventual consistency: writes propagate to replicas asynchronously. Reads may be stale for a bounded time window. Social feeds. Analytics. Much higher availability.
- Draw a timeline for both: what does a user see in each model during a network partition?

**Tuesday (2.5 hrs):**
- CAP Theorem: in a network partition, you must choose Consistency or Availability.
- Classify 6 systems: PostgreSQL (CP — favors consistency), Cassandra (AP — favors availability), Redis (CP by default), DynamoDB (tunable), Zookeeper (CP), MongoDB (tunable).
- Memorize the classification — this is a 30-second question in interviews.
- PACELC: extends CAP to normal operation (no partition). Even without partition, you trade latency for consistency.

**Wednesday (1.5 hrs):**
- Practice: "When would you choose eventual consistency? Give 3 specific examples with reasoning." (Example: "Twitter likes counter — users tolerate a like count that's a few seconds stale. Eventual consistency gives us 10× better write throughput.")

**Thursday (2.5 hrs):**
- Design Distributed Rate Limiter — requires consistency decisions. If we use Redis (CP), a brief Redis outage could block all requests. If we use in-memory per-node rate limiting (AP), a user could send 5× the limit by hitting different nodes. State this trade-off explicitly.

**Saturday (3.0 hrs):**

- Hour 1: HLD reading: Scaler CAP/PACELC lecture + Master-Slave Replication

### Week 27: HLD Concept 3 + 4 — Database Selection + Message Queues

**Database Selection Decision Tree:**

```
1. Do you need ACID transactions across multiple records?
   YES → SQL (PostgreSQL, MySQL)
   
2. Does your schema change frequently or is it highly variable?
   YES → NoSQL document (MongoDB)
   
3. Do you need to scale horizontally to billions of records?
   YES → NoSQL (Cassandra, DynamoDB)
   
4. Do you need full-text search and ranking?
   YES → Elasticsearch (not a primary DB — use alongside)
   
5. Do you need time-series data (metrics, events)?
   YES → InfluxDB or Cassandra
   
Default for most applications: PostgreSQL. Only deviate when you have a specific reason.
```

**Message Queue Concepts (Kafka vs RabbitMQ vs SQS):**

| Property | Kafka | RabbitMQ | SQS |
|---|---|---|---|
| Delivery guarantee | At-least-once (configurable) | At-least-once | At-least-once |
| Message persistence | Yes (log-based, replay) | Optional (expires after ack) | Configurable |
| Throughput | Millions/sec | Thousands/sec | Thousands/sec |
| Use when | High-throughput event streaming, replay needed | Complex routing, lower volume | Simple queue, AWS native |
| Key concept to know | Consumer groups, partition offsets | Exchange types, routing keys | Visibility timeout, DLQ |

**Week 28 — Facebook Messenger / WhatsApp:**

The unique challenge: **real-time delivery with offline handling**.

Components: WebSocket gateway (connection service), Message service (store-and-forward), Notification service (for offline users), Message storage (Cassandra — write-heavy, partition by conversation_id), Presence service (Redis — who is online).

Trade-off to articulate: **Push vs Pull.** Push (WebSocket): low latency, requires persistent connection, complex offline handling. Pull (long polling): simpler, higher latency. Decision: push for online users, queue-based notification for offline users.

Scale challenge: 100B messages/day → 1M+/second peak. Cassandra partitioned by conversation_id handles this. Hot partitions (viral chats) addressed by sub-partitioning by time window.

**Week 29 — Twitter/Facebook News Feed:**

The unique challenge: **fan-out at celebrity scale**.

Fan-out-on-write (push): on post, immediately write to all followers' feed caches. Fast reads. Problem: a celebrity with 10M followers → 10M writes per post.

Fan-out-on-read (pull): on load, fetch all posts from followed accounts, merge. No write amplification. Problem: reading 1000 accounts' posts on every feed load is slow.

Real solution (hybrid): push for users with < 10K followers. Pull for celebrity accounts. Merge at read time. Cache the merged feed.

**Week 30 — Google Typeahead:**

The unique challenge: **sub-100ms response for prefix matching**.

Key components: Trie data structure (in-memory, prefix lookup), Top-K ranking (frequency + recency weighted), CDN caching (cache suggestions per prefix at the edge, update hourly), Data aggregation (batch processing of search logs to update trie daily).

Trade-off: Real-time trie updates vs batch updates. Real-time: stale within seconds. Batch: stale for up to 1 hour. For autocomplete, hourly stale is acceptable. "Breaking news" terms can be handled by a real-time overlay on top of the daily batch trie.

### HLD Component Selection

| Requirement | Component | Avoid |
|---|---|---|
| Sub-ms reads on hot data | Redis | SQL for this |
| Full-text search + ranking | Elasticsearch | SQL LIKE |
| High write throughput (millions/sec) | Cassandra, Kafka | PostgreSQL for this scale |
| ACID transactions, moderate scale | PostgreSQL | Cassandra (no joins, no transactions) |
| Async job processing | Kafka, SQS, RabbitMQ | Synchronous HTTP calls |
| Geo-proximity queries | PostGIS, Redis GEOADD | Plain lat/lng in SQL |
| Global low-latency static content | CDN | Origin server |
| Distributed locking | Redis SETNX, ZooKeeper | Application-level mutex |
| Session storage | Redis | SQL (too slow for session lookup) |

### LLD Pattern Decision Guide

| When you hear "add [X] without changing existing code" | → OCP. Factory or Strategy pattern. |
|---|---|
| When you hear "notify multiple systems when [event] occurs" | → Observer / Event Bus |
| When you hear "this object needs to go through multiple states" | → State Machine |
| When you hear "build this object step by step with optional fields" | → Builder |
| When you hear "we need to undo the last N actions" | → Command |
| When you hear "we need one shared instance across the system" | → Singleton (use sparingly) |
| When you hear "wrap this with logging/retry/rate limiting" | → Decorator |
| When you hear "create objects without specifying exact class" | → Factory / Abstract Factory |
